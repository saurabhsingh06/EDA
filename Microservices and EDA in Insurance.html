Architecture Note

Microservices and Event-Driven Architecture in Insurance

Kafka set-up flow diagram

1Background

In an insurance company, a single event triggers many processes in the background:

  1. Quote suggestion
  2. KYC
  3. Pricing engine
  4. Underwriter management
  5. Fetching details from multiple vendors such as Vahan and HyperVerge
  6. Payment gateway integration
  7. Payment
  8. Accounting
  9. Re-insurance
  10. Policies and endorsements
  11. IRDAI reporting
  12. Claims
  13. ...and more

2Why Microservices

At scale, a monolithic architecture doesn't work, so we introduced a microservice architecture.

In a distributed system, the services need a way to communicate with each other. For this we need Event-Driven Architecture (EDA).

3Communication Options

HTTP calls are the basic way to communicate, but they become a single point of failure (SPOF).

The alternatives we considered:

Redis Streams SQS + SNS EventBridge Kafka RabbitMQ

3.1 Redis Streams

RAM concern

For scale, assume traffic of around 10M (in our case it will be more than that).

  • Redis Streams stores all messages in RAM.
  • At scale, RAM is expensive, so the cost goes up.
  • If a consumer is not good enough (slow or lagging), messages pile up in memory.
  • Insufficient RAM can then crash the server.

3.2 SQS with SNS

Fire and forget
  • In SQS, a single message can be consumed by only one consumer, which must delete the message after consumption.
  • This can be solved by using SNS for a fan-out architecture.
  • However, SNS works on the fire-and-forget principle.
  • For a regulatory product, we cannot tolerate missing messages.
  • Hence these services are mostly used for communication and notification purposes.

3.3 EventBridge

Vendor lock-in
  • It is a great EDA solution. We explored it extensively while finalizing, and it has strong community support and is handy to use.
  • Internally it uses many other AWS services such as SQS and S3.
  • It is cheaper in the initial phase.
  • However, using it long term locks us in with AWS.
  • Switching to another provider becomes a nightmare.
  • AWS also charges more at scale.

3.4 Kafka vs RabbitMQ

One of the cheat sheets I follow to decide between Kafka and RabbitMQ:

RequirementBetter fit
Background jobs🐇 RabbitMQ
Worker queue🐇 RabbitMQ
Complex routing🐇 RabbitMQ
Task acknowledgement🐇 RabbitMQ
High-volume event stream🟠 Kafka
Event replay🟠 Kafka
Many independent consumers🟠 Kafka
Event sourcing🟠 Kafka
Streaming analytics🟠 Kafka
Data pipeline🟠 Kafka
ML event pipeline🟠 Kafka
Microservice event backbone🟠 Kafka

4Decision

Our requirements fit Kafka more closely: event replay, high throughput, and multiple consumers working independently. Hence we chose Kafka over RabbitMQ.
